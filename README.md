## ทำไมถึงวางแบบนี้

**ตรรกะที่ต้องอะตอมมิกอยู่ในฐานข้อมูล ไม่ใช่ใน Edge Function**
ของเดิมได้ความอะตอมมิกฟรีจากทรานแซกชันของ `better-sqlite3` ซึ่งเป็น synchronous และอยู่ในโพรเซสเดียวกับฐาน
บนคลาวด์ Edge Function คุยกับฐานข้ามเครือข่าย ถ้าอ่าน-คิด-เขียนจากฝั่งนั้น สองคนกด "จ่ายของ" พร้อมกันจะอ่านยอดเดียวกันแล้วตัดสต็อกซ้อนกัน
จึงย้ายตรรกะทั้งก้อนลงเป็นฟังก์ชันใน Postgres (`api_issue`, `api_receive`, `api_adjust`, …) — **เรียก 1 ครั้ง = 1 ทรานแซกชัน + ล็อกแถวด้วย `FOR UPDATE`**
Edge Function เหลือหน้าที่แค่ตรวจสิทธิ์ แปลงข้อมูล และแปลง error เป็น HTTP status

**ทางเข้าฐานมีประตูเดียว**
ทุกตารางเปิด RLS แบบไม่มี policy และถอนสิทธิ์ `anon`/`authenticated` ทิ้ง → เรียกผ่าน PostgREST ด้วย anon key ไม่ได้เลย
เข้าได้ทางเดียวคือ Edge Function ที่ต่อด้วย service role และตรวจสิทธิ์เองในโค้ด (สถาปัตยกรรมเดียวกับของเดิมที่ตรรกะสิทธิ์อยู่ชั้นเดียว)

**token ใช้ยืนยันแค่ว่าใครเป็นใคร** — บทบาท/แผนก/สถานะบัญชี อ่านจากฐานทุกคำขอ
(บทเรียนจากรุ่น LAN: เชื่อค่าใน token แล้วปิดบัญชีไม่มีผลถึง 12 ชม. · ตั้งผู้ดูแลคลังแล้วสิทธิ์ไม่มาจนกว่าจะออกแล้วเข้าใหม่)

**เส้นทาง API ชื่อเดิมทุกเส้น** หน้าเว็บจึงแก้แค่ที่อยู่ฐานใน `web/config.js` ที่เดียว ไม่ต้องรื้อโค้ดหน้าเว็บ

## ขั้นตอนขึ้นระบบ (ทำครั้งเดียว)

### 1. Supabase
```bash
npm i -g supabase          # หรือ scoop/brew ตามเครื่อง
supabase login             # เปิดเบราว์เซอร์ให้ล็อกอินเอง
supabase link --project-ref <project-ref>
supabase db push                                   # สร้างตารางและฟังก์ชันทั้งหมด
supabase secrets set APP_TOKEN_SECRET="<สุ่มยาว ๆ 64 ตัวอักษร>"
supabase functions deploy api --no-verify-jwt      # ⚠️ ต้องมี --no-verify-jwt เพราะเราตรวจ token เอง
```

ใส่ข้อมูลตัวอย่าง: เปิด **SQL Editor** บนหน้าเว็บ Supabase → วางเนื้อไฟล์ `supabase/seed-demo.sql` → Run

> `APP_TOKEN_SECRET` คือกุญแจเซ็น token — เปลี่ยนเมื่อไร ทุกคนต้องเข้าสู่ระบบใหม่
> `SUPABASE_DB_URL` ไม่ต้องตั้ง Supabase ใส่ให้เอง

### 2. หน้าเว็บ
- แก้ `web/config.js` เป็น `window.API_BASE = 'https://<project-ref>.supabase.co/functions/v1';`
  (**ห้ามใส่ `/api` ต่อท้าย** โค้ดหน้าเว็บเติมให้เอง) — หรือตั้ง repo variable ชื่อ `API_BASE` แล้ว workflow จะเขียนให้ตอน deploy
- push ขึ้น GitHub → **Settings → Pages → Source: GitHub Actions**
- จำกัดว่าใครเรียก API ได้: `supabase secrets set APP_ALLOWED_ORIGINS="https://<user>.github.io"`
  (เว้นว่าง = ปล่อยทุกโดเมน ใช้ได้เฉพาะตอนทดสอบ)

## ทดสอบในเครื่องก่อนขึ้นจริง

ทดสอบได้ครบทั้งระบบโดยไม่ต้องมี Docker — ใช้ PostgreSQL กับ Deno แบบพกพา

```bash
# 1) ฐานข้อมูล
initdb -D pgdata -U postgres -A trust -E UTF8 --locale=C
pg_ctl -D pgdata -o "-p 5433" -l pg.log start
createdb -h 127.0.0.1 -p 5433 -U postgres equipment
psql -h 127.0.0.1 -p 5433 -U postgres -d equipment -f supabase/migrations/0001_schema.sql
psql -h 127.0.0.1 -p 5433 -U postgres -d equipment -f supabase/migrations/0002_logic.sql
psql -h 127.0.0.1 -p 5433 -U postgres -d equipment -f supabase/migrations/0003_drafts_images.sql
psql -h 127.0.0.1 -p 5433 -U postgres -d equipment -f supabase/seed-demo.sql

# 2) หลังบ้าน (พอร์ต 8000)
DB_URL="postgres://postgres@127.0.0.1:5433/equipment" APP_TOKEN_SECRET=dev \
  deno run --allow-net --allow-env --allow-read supabase/functions/api/index.ts

# 3) หน้าเว็บ — เสิร์ฟโฟลเดอร์ web/ ที่พอร์ตอื่น (เช่น 8080) แล้วตั้ง API_BASE เป็น http://localhost:8000
```

**ผลทดสอบรอบล่าสุด** (ชุดเดียวกันนี้รันกับ Supabase ของจริงแล้วด้วย — ผ่าน 62/62 เช่นกัน)
- ตรรกะใน Postgres **26/26** — รับเข้า · จ่ายครบ/บางส่วน · จ่ายเกินไม่ได้ · ขอเกินสต็อกไม่ได้ · รวมรายการซ้ำ ·
  ครุภัณฑ์ยืม-คืน · ปรับยอดบังคับเหตุผล · ปฏิเสธบังคับเหตุผล · แจ้งเตือน · เลขที่ใบเบิกไม่ซ้ำ · `api_reconcile()` ได้ 0 แถว
- API ผ่าน HTTP **62/62** — เข้าสู่ระบบด้วยแฮชเดิม · สิทธิ์ทุกบทบาท · ร่าง/ส่ง/ยกเลิก/ลบ · จ่ายของ ·
  **กดจ่ายพร้อมกัน 2 ครั้งได้ `200`+`409` ตัดสต็อกครั้งเดียว** · รูปสินค้า · CSV (ราคา ณ วันจ่าย) · CORS ข้ามโดเมน
- หน้าเว็บจริงบนเบราว์เซอร์: เข้าสู่ระบบข้ามโดเมน → เปิดคิวคลัง → กดอนุมัติและจ่ายของ → ตัดสต็อกถูกต้อง · 0 console error

## ต่างจากรุ่น LAN ตรงไหน

| เรื่อง | รุ่น LAN | รุ่นนี้ |
|---|---|---|
| ตรรกะสต็อก | `services/*.js` ในทรานแซกชัน SQLite | ฟังก์ชัน `api_*` ใน PostgreSQL |
| รูปสินค้า | ไฟล์บนดิสก์เซิร์ฟเวอร์ | ตาราง `item_images` (คลาวด์ไม่มีดิสก์ถาวรให้เขียน) |
| เวลา | epoch ms ใน SQLite INTEGER | epoch ms ใน `bigint` (ไดรเวอร์ถูกตั้งให้แปลงเป็น number ไม่ใช่สตริง) |
| จำนวน/ราคา | REAL + ปัด 2 ตำแหน่งในโค้ด | `numeric(14,2)` ปัดให้ในตัว |
| สำรองข้อมูล | คัดลอกไฟล์ทุก 6 ชม. | Supabase สำรองให้ตามแพ็กเกจ |

## กับดักที่เจอตอน deploy (บันทึกไว้กันลืม)

- **`gen_random_bytes()` ของ pgcrypto ใช้ไม่ได้บน Supabase** — extension ถูกติดตั้งใน schema `extensions`
  ซึ่งไม่อยู่ใน search_path ของฟังก์ชัน → `db push` ล้มกลางคัน · แก้ด้วยการใช้ `gen_random_uuid()` ที่มากับ PostgreSQL 13+ ในตัว
- **`actions/configure-pages` ใส่ `enablement: true` ไม่ได้** — `GITHUB_TOKEN` ไม่มีสิทธิ์เปิด Pages เอง job จะล้มทั้งงาน
  ต้องเปิดที่ Settings → Pages → Source: GitHub Actions ด้วยมือครั้งเดียวก่อน
- **workflow ไม่ยิงอัตโนมัติในครั้งแรกที่สร้าง branch** — ต้อง push อีกครั้งหรือกด Run workflow เอง
- **`supabase login` ใช้ในสภาพแวดล้อมที่ไม่มี TTY ไม่ได้** — ต้องรันในเทอร์มินัลของผู้ใช้เอง (โทเคนถูกเก็บในเครื่อง)
- **`functions deploy` อาจล้มด้วย 500 แบบสุ่ม** — ลองใหม่อีกครั้งผ่านเลย ไม่ใช่ปัญหาที่โค้ด

## ยังไม่ได้ทำ

- **ย้ายข้อมูลจริงจาก SQLite → Postgres** (ยังไม่มีสคริปต์ · ไฟล์ฐานข้อมูลอยู่ที่เครื่องเซิร์ฟเวอร์ในออฟฟิศ)
- นำเข้าพนักงาน 309 คนจากระบบใบสำคัญจ่าย (รุ่น LAN มี `src/import-users.js` ต้องเขียนใหม่ให้ยิงเข้า Postgres)
- แจ้งเตือน LINE · ทยอยจ่ายหลายรอบต่อใบ · เชื่อมระบบจัดซื้อ/HR
- ครุภัณฑ์ที่ยืมไปตัดงบแผนกถาวร (รับคืนแล้วไม่คืนงบ) — เป็นเรื่องนโยบายบัญชี ยกมาจากรุ่น LAN ทั้งดุ้น ยังไม่ตัดสินใจ

## ก่อนเอาข้อมูลจริงขึ้น ต้องคิดให้จบก่อน

ตอนนี้ระบบอยู่บนอินเทอร์เน็ตสาธารณะ ใครเปิด URL ก็เจอหน้าเข้าสู่ระบบ (ต่างจากรุ่น LAN ที่เข้าได้เฉพาะในออฟฟิศ)
ถ้าจะเอาข้อมูลพนักงานจริงขึ้น อย่างน้อยควรมี: บังคับเปลี่ยนรหัสผ่านที่ตั้งจากระบบเดิม · จำกัด `APP_ALLOWED_ORIGINS` ·
เปิด rate limit ของ Supabase · และตรวจสอบกับนโยบายข้อมูลของบริษัทว่าให้เก็บข้อมูลพนักงานบนคลาวด์ต่างประเทศได้หรือไม่
